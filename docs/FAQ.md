# FAQ

## Is the frontend still mock-backed?

No. The active React application uses the authenticated local runtime API for provider catalog, provider profiles, workflows, recovery, audit data, and workflow controls. Deterministic mocks remain only inside automated test fixtures.

## Is Atrin vendor-specific?

The orchestration core is vendor-neutral. Providers select adapter IDs and capabilities through configuration. The workflow engine does not contain hardcoded vendor branches.

## Which provider transports are available?

The current registry includes configurable web, generic HTTP API/chat-completions, MCP, A2A, and ACP adapter families.

## Are credentials stored in the repository?

No. Provider examples reference environment variables for credentials. The runtime token is generated by the backend and the desktop UI keeps it only in the current session.

## Are plugins sandboxed?

Plugins execute in dedicated worker processes, each placed in its own process group with CPU-time, memory, open-file, and process-count rlimits (`RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_NOFILE`, `RLIMIT_NPROC`), and registry records include a file hash. Termination (timeout or cleanup) signals the whole process group, not just the direct worker PID, so a plugin cannot outlive shutdown by spawning children. The import/call AST validator blocks direct dangerous imports and calls, including dynamic dunder-attribute bypasses via `getattr`/`setattr`/`globals`/`locals`/`vars`. This is meaningful process isolation and resource containment, but it is still not a complete OS/container sandbox (no filesystem chroot, no network namespace). Only trusted administrator-controlled plugins are supported; untrusted third-party plugin uploads remain unsupported.

## Can a workflow safely resume after a crash?

Workflow state, checkpoints, operation IDs, and idempotency records are persisted. Whether an external side effect can be conclusively verified after a crash depends on the provider's own operation/status/evidence API. Ambiguous side effects are not silently retried.

## Does CI test a real browser?

Yes. CI installs Chromium and runs a Playwright journey against the real React build and FastAPI runtime using a deterministic test provider. No real provider credentials are exposed.

## Is production readiness proven for every provider?

No. The repository has a hardened RC baseline. Each real provider/account configuration still needs controlled credential/session validation, and the final Windows installer needs clean-machine validation before production deployment.
